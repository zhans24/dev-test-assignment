# Задача 1. Распределение заказов по филиалам

Сервис доставки для магазинов с несколькими филиалами (складами). Магазин присылает заказ, и его нужно закрепить за филиалом, который соберёт заказ и отправит курьера.

В `src/` уже есть заготовка: модели, расчёт расстояния, первая версия `assignBranch` и HTTP-сервер на `node:http`. Данные лежат в `data/*.json`, всё хранится в памяти.

## 1. Баг

Один тест в `test/router.test.ts` падает: заказ уходит не в ближайший филиал. Найдите причину и исправьте.

## 2. Правила выбора филиала

Учитываются только активные филиалы того же магазина. Правила проверяются по порядку, срабатывает первое подходящее.

| Правило | Когда срабатывает |
|---|---|
| `manual` | у заказа задан `manualBranchId`, и этот филиал активен |
| `single` | у магазина один активный филиал |
| `pickup_point` | у заказа есть `pickupPointId`, и он закреплён за филиалом (`pickupPointIds`) |
| `city` | в городе заказа ровно один филиал магазина |
| `geo` | ближайший филиал по координатам заказа. Если в городе заказа несколько филиалов, выбираем ближайший из них, иначе — ближайший из всех |
| `unassigned` | ничего не подошло, например у заказа нет координат |

Сейчас написаны `manual`, `single` и `geo`.

При выборе по координатам расстояние до филиала должно быть не больше 42 км. Если ближайший подходящий филиал дальше, API возвращает `branchId: null` и `rule: "too_far"`. Это относится и к выбору запасного филиала при заполненном лимите.

## 3. Дневной лимит

У филиала есть `dailyLimit` — сколько заказов он принимает за сутки. Сутки считаются по времени Алматы (UTC+5) от `createdAt` заказа.

- Если филиал, выбранный правилом `single`, `pickup_point`, `city` или `geo`, уже заполнен, заказ уходит в ближайший незаполненный филиал магазина с правилом `geo`. Если такого нет — `unassigned`.
- `manual` лимит не проверяет: менеджер решил сам.

## 4. API

`POST /orders/:id/assign` — распределить заказ.

```json
{ "orderId": "o-101", "branchId": "b-ala-1", "rule": "pickup_point" }
```

- нет такого заказа — `404`;
- повторный вызов для того же заказа возвращает то же распределение и не занимает лимит ещё раз. Интеграции магазинов нередко шлют один запрос дважды.

`GET /branches/:id/load?date=2026-11-16` — загрузка филиала за дату по Алматы.

```json
{ "branchId": "b-ala-1", "date": "2026-11-16", "assigned": 3, "limit": 3 }
```

- нет `date` или дата некорректная — `400`;
- нет такого филиала — `404`.
